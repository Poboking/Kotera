## 2. 什么进这张表（判定口径）

1. **随包语料数据本体**的缺陷（ERB/ERH/CSV 内容错误、声明与调用不一致、表尺寸与脚本假设不符）⇒ 本表在册，**走 §3 内容补丁修复**，并同步登记唯一官方 bug 集 `docs/UPSTREAM-BUG-PR.md` A 类。
2. **引擎判定 / 自造串 / 门控问题 / 移植侧语义实现错误** ⇒ 不进本表的补丁通道，**移交引擎侧直接修为真确语义**（ADR-005 2026-11-17 分类处置口径），登记 `UPSTREAM-BUG-PR.md` B 类或 `verify-notes.md`；测试装置假绿 → CONTRACT-REPORT-DEDUP3 台账；玩家私装缺件 → 记「缺件候选」留证，不立项。不得因「官方同形」放弃在册 bug。
3. 每行必须带：端点签名或正文样张路径、语料 `文件:行号`、判官方同形时的 C# 证据。
4. 状态机：`待判定 → （主人拍板）待修 / 官方正确设计不修 / 玩家缺件 / 等上游 / 出包侧缺陷 / 移交引擎侧直修` → `已修（补丁 id）` / `已修（引擎直修，附落点）` / `已修（出包侧）` / `已判结`。
   「出包侧缺陷」= 语料与引擎各自都对、混装才炸（CB-002）；判它必须给出**同源数据下不越界**的正证，
   不能只引「越界必崩」的裸下标锚（那只说明后果，不说明本案同形）。
5. 「官方正确设计不修」是**行为判词**（不再是旧称「官方同形不修」），必须带 C# `文件:行号` 指到原版同一条路径的同一后果；
   台账文字、既有判例、报错串相似都不算证据（D6 复核 2026-11-07：K51 与 CB-002 两处旧判词即因此翻案）。
   `error-texts.yaml` 的「不改-同形」是**文案判词**，两类标签不可混用。若判定对象是官方 **bug**（非正确设计），
   则按第 2 条移交引擎侧直修或第 1 条走内容补丁，不得用本条「不修」判词豁免。

## 3. 内容补丁的多主机分发机制（修包唯一通道）

语料根不进 git、两机各持只读副本 ⇒ 修复必须是**仓库内资产、编译期应用**：

1. **补丁资产**：`devtools/corpus-patches/<id>.patch`（统一 diff）+ `devtools/corpus-patches/index.yaml`
   （id、目标文件、**目标文件 sha256**、适用语料版本、病灶/修法摘要、状态）。
   `root: game`（可选，缺省 `corpus`）把目标解析根从 `<游戏根>/ERB` 换到游戏根，用于
   `CSV/_Rename.csv` 这类与 ERB 平级、但同样随包的数据；`skip-sha256`（可选）登记
   「已知不进入本链的其它版本」（两类语义见本节末注），其余未知 sha 仍判红。
2. **应用点**：`:tools:erbcc:compileCorpus`（及一切喂 erbcc 的流程）编译前把补丁应用到**临时副本**再喂编译器；
   `root: game` 的目标**同时**在 `:app:stageGameAssets` 落 assets 时替换（硬链接只读，删链接后写修后字节），
   否则会出现「erbc 修了、随包 CSV 没修」的半截修复。
   应用失败（目标 sha 不符 / diff 上下文不匹配）即**判红**，不许静默跳过——防上游语料换版漂移。

### 4.1 为什么不是掩盖：语义与原版同形 + 硬闸在册

1. **原版同形**：Emuera 装载期函数体解析失败时**不删标签**，而是给函数打 `ErrMes`——
   `ErbLoader.cs:995-1010`（`ParseFunctionWithCatch` 捕获 → `label.ErrMes = Lang.Error.CalledFailedFunc.Text`，
   继续装载其余函数）；运行期走到该函数即抛：`CalledFunction.cs:133`（`errMes = TopLabel.ErrMes`）→
   `Process.cs:1017-1035`（`throw new CodeEE(currentLine.ErrMes)`）。调用点也会被静态标记：
   `FunctionIdentifier.cs:3544-3548`（`TopLabel.IsError ⇒ func.IsError = true; func.ErrMes = …`）。
   原版文案 `Lang.cs:2450`「ロード時に解析に失敗した関数が呼び出されました」。
   移植侧「入口 THROW 桩」是同一形态；strict 档（拒绝落盘）反而比原版更严，属本项目的刻意加严。
2. **不静默**：清单外失败判红、清单项未命中判红（`ParseFailureToleranceTest`）、
   `degraded-slices` 必须等于清单条数、逐条 `degraded` 文案进 manifest、出包需显式
   `--allow-degraded-corpus`、`applied_corpus_patches` 独立列随包自证（D8/D8b）。
   与「改白名单让错误消失」的掩盖手法相反：这里每一条都必须点名、留痕、随包可查。
3. **不是唯一出路**：数据层能修的先修数据（§3）。CB-005 把 4 条 `CASE [[…]]` 从清单里消灭（13→8），
   是「降级 → 数据补丁」的正确退出路径判例。

## 5 上游 PR 出口（lane corpus-pr，2026-11-10）

> 目的：把 §1 里所有**已修（补丁 …）**的语料缺陷，按 id 打成可提交上游的补丁包；主人将来挑一批交给 eraTW 语料原作者/维护者。本节只定「怎么出口」，不改 §1 的判定。

### 5.1 单一映射规则（台账是唯一真源）

- 台账 §1 的**一**行 ⇔ `devtools/corpus-patches/index.yaml` 的**一条**条目 ⇔ `out/corpus-pr/<id>/` 的**一个** bundle，三面 id 同名。
- 只有处置列为「已修（补丁 <id>）」的行才出口；其它状态（待裁定 / 等上游 / 官方正确设计不修 / 已修（出包侧） / 移交引擎侧直修）**跳过并告警**，不生成 bundle、也不判红。
- index.yaml 有条目、台账却没认账 ⇒ **红**；台账认了、index.yaml 没条目 ⇒ **红**；补丁资产缺失 ⇒ **红**。
- 宁红不猜：解析失败、未知字段、sha 形状不对、id 与文件名对不上，一律判红。
### 5.2 bundle 结构（每个 id 一个目录）

```
out/corpus-pr/<id>/
  README.md       # 病灶 / 证据 / 修法 / 风险 / 上游路径（PR 描述底稿）
  <id>.patch      # unified diff，字节 = index.yaml 指向的补丁资产（原样）
  manifest.json   # 机器判据：corpus/target/root、bad/fixed/patch 三个 sha256、
                  # 台账行号与行 sha256、建议分支与 commit subject、文件清单
```

- `manifest.patch.sha256` 必须等于 `<id>.patch` 实际 sha256（自洽判据，测试钉死）。
- `ledger.row_sha256` 是台账该行 sha256：台账改了而 bundle 没重生成 ⇒ `--check` 判红。
- 确定性：同输入两次生成逐字节相同（键排序、LF、无时间戳、无绝对路径）。

### 5.3 生成与校验

```
python devtools/export_corpus_pr.py            # 生成 out/corpus-pr/<id>/
python devtools/export_corpus_pr.py --check    # 只校验不写盘（CI / 提交前）
python devtools/test_export_corpus_pr.py       # 定向回归（离线、无 Gradle）
```
### 5.4 提交清单（主人去上游提 PR 时照这个走）

1. **钉上游**：以 eraTW 语料原作者发布页/仓库为准（本工具离线、不代填 URL，提交前由主人钉住仓库与目标分支）。
2. **分支**：`eratw-corpus-fix/<id>`（一 id 一分支，便于单独 review / 单独拒收）。
3. **commit**：`corpus(<id>): <summary 首句>`（导出器给在 `manifest.upstream.commit_subject`）；body 贴 README 的「病灶/证据/修法」+ manifest 的 sha256 三件套。
4. **PR 描述**：一句病灶 + 复现链（玩家操作）+ 影响面（角色/衣装/存档）+ 修法二选一（§5.5）+ 「只改语料文本、不动引擎」。

   - `#DIM CONST MAXPANTS=34` 是笔误还是有意（对象号空间到 35）？
   - 抬 `MAXPANTS` 会让旧存档 `PANTS_TEMP` 维度变长，可接受吗？

   - 4.980/4.981 同形，是否已在更高版本修过（有则改判「已上游修复」并撤本仓补丁）。
6. **回填**：上游合入后把台账处置改成「已上游修复（版本/commit）」并撤 `index.yaml` 条目（或降级 `skip-sha256`），保持三面一致。
